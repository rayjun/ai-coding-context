# 代码审查 (Code Review)

## 概览
9 步流程第 6 步的审查标准。与 plan-review（方案审查）互补：plan-review 审「计划是否可行」，code-review 审「代码是否达标」。

## 何时使用
- Step 5 执行完成后、Step 7 验证之前（moderate+ 必做）。
- 任何进入生产路径的代码变更。

## 审查前置条件：工具证据

**硬性要求：审查必须基于实际运行的工具输出，不能只靠读代码。** LLM 读代码存在共享认知盲区，工具输出是对冲。

Step 5 完成后立即收集（按项目技术栈选择）：
- 编译 / 类型检查：`cargo check` / `tsc --noEmit` / `go build` / `mvn compile` 等
- Lint：`clippy` / `eslint` / `golangci-lint` / `ruff` / `shellcheck` 等
- 测试：项目测试命令 + 覆盖率输出（有 coverage 工具时）

证据要求：
- 每条证据引用**具体命令**和**真实输出片段**（非转述、非编造）。
- 工具输出含 error / warning 时逐条说明是否已处理、如何处理。
- 无工具证据的审查结论（尤其「通过」）判 fail。

## 审查维度

### 1. 安全性 [pass | warn | fail]
- 输入校验：外部输入是否在边界校验（注入、路径穿越、类型混淆）。
- 权限与敏感数据：最小权限、密钥不落地、日志不泄漏。
- 资源：内存 / 文件 / 连接的生命周期，是否有泄漏风险。

### 2. 正确性 [pass | warn | fail]
- 边界条件：空值、零值、上限、溢出、并发竞争。
- 错误路径：每环节失败时的行为（超时、异常、数据不合法）。
- 幂等性与重试是否安全。

### 3. 可维护性 [pass | warn | fail]
§3 哲学 checklist：
- **过度设计**：是否写了不需要的抽象 / 灵活性 / 配置项。
- **孤儿代码**：未使用的 import / 变量 / 函数 / 死分支。
- **命名一致性**：与项目风格一致，命名表达意图。
- **外科手术**：每处改动可追溯到需求；无顺手重构 / 格式混改。
- 重复逻辑、过紧耦合、脆弱设计。

### 4. 测试覆盖 [pass | warn | fail]
- 生产业务逻辑是否有测试；测试是否真正断言（非恒真）。
- 负路径 / 边界测试是否覆盖关键分支。
- 覆盖率证据（有工具时）：是否达标；未达标分支是否有合理解释。

### 5. 需求符合度 [pass | warn | fail]
- 每项需求 → 代码 → 测试 一一对应。
- 有无未要求的功能（推测性功能）。

## 输出格式

```
## 代码审查 · <scope>

### 1. 安全性  [pass | warn | fail]
- 证据：<命令> → <输出片段>
- 发现：...
- 建议：...

### 2-5. 正确性 / 可维护性 / 测试覆盖 / 需求符合度（同构）

## 工具证据清单
| 命令 | 结果 | 说明 |
|------|------|------|
| cargo check | 0 error / 2 warning | warning W1 已处理：... |

## 结论
<N> warn / <M> fail。fail 项必须在 Step 7 前修复并重跑审查。
```

## 质量评估标准（EVAL）

```
EVAL 1: 五维度全覆盖
问题: 审查报告是否逐一覆盖安全性、正确性、可维护性、测试覆盖、需求符合度 5 个维度？
Pass: 5 个维度各有独立段落和明确评级
Fail: 遗漏维度，或多维合并敷衍带过

EVAL 2: pass/warn/fail 评级
问题: 每个维度是否给出了明确的 pass、warn 或 fail 评级？
Pass: 每维度都有三选一明确标注
Fail: 只有描述没有评级，或模糊表述（"大体可以"）

EVAL 3: fail 项有具体修改建议
问题: 每个 fail 项是否附带了可操作的修改建议？
Pass: 指出改什么、怎么改
Fail: 只说"不行"没有建议

EVAL 4: 工具证据
问题: 审查是否实际运行了编译/lint/类型检查/测试并引用真实输出？
Pass: 每维度或工具证据清单中有具体命令 + 真实输出片段，输出可复核
Fail: 无工具证据；或只转述"测试通过"而无输出；或证据是编造的

EVAL 5: §3 哲学 checklist
问题: 可维护性维度是否覆盖过度设计 / 孤儿代码 / 命名一致性 / 外科手术四项？
Pass: 四项各有明确判定
Fail: 未检查或检查缺失

EVAL 6: 需求可追溯
问题: 需求符合度维度是否建立 需求→代码→测试 的对应？
Pass: 列出对应关系并指出无对应项
Fail: 只笼统说"符合需求"
```

## 与 plan-review 的关系
- plan-review（第 2续步）：审计划（数据流 / 并发 / 接口 / 测试 / 运维）→ 发现实现前能发现的问题。
- code-review（第 6 步）：审代码（安全 / 正确 / 可维护 / 测试 / 需求）→ 带工具证据验收实现。
- 两者维度互补不重复；code-review 的测试覆盖维度引用实际 coverage 证据，不是 plan 里的测试策略。
